Some work needs a key. To read your Plausible numbers, a bot has to send Plausible's API a key
that only you can make. A bot keeps such things in its **vault**: API keys, passwords, tokens. You
give one once, and the bot uses it from then on, in its conversation, in its subagents and in its
automations, without asking again.

A bot never sees a secret's value. It knows the secret by its **name**, and OpenKumi puts the
value in as a request leaves the computer. So a secret is not in the conversation, not in what the
model's service is sent, and not in a file the bot keeps.

## Giving a bot a secret

<Steps>

1. **Ask for the work.** "How many visitors did openkumi.ai have this week?" The bot sees that
   it has no key for Plausible.

2. **The bot asks, in a card.** A card appears in the conversation, on the computer and on the
   iPhone: what it needs ("Plausible API key"), the name it will be kept under, and the one site it
   will be sent to. When the bot knows where you make such a key, the card links there.

3. **Type or paste it into the card, and choose Save.** The value goes straight to the server and
   into the vault. The bot is told only that it is there, and carries on.

</Steps>

**Not now** tells the bot you said no. A card that nobody answers stops waiting after 25 minutes;
the bot says what it needed, and can ask again.

You can also add one yourself, before any bot asks: **Settings → Bots →** the bot **→ Secrets →
Add a secret** on the computer, or **Secrets** in the bot's settings on the iPhone.

<Aside type="caution" title="Do not paste a key into a message">
A message is read by the AI service that powers the bot, and is kept in the conversation. If you
do it anyway, the bot puts the key in its vault and the server takes it out of the conversation it
keeps, but the service has already read it. Make a new key if that matters.
</Aside>

## A secret is for one site

Every secret names the site it may be sent to, as the site's address names it: `plausible.io`, or
`api.stripe.com`. It is sent there and nowhere else:

- to exactly that host. `plausible.io` does not cover `app.plausible.io`; name both if both are
  needed, separated by commas;
- over `https`. Plain `http` is allowed only to an address written as numbers, of this computer
  (`127.0.0.1`) or of the local network, such as a Home Assistant at `http://192.168.1.20:8123`.
  A name (`localhost`, `homeassistant.local`) is not enough without `https`, and neither is an
  address on Tailscale, as with OpenKumi's own apps. Plain `http` is as safe as the network the
  computer is on, so think twice on a network that is not yours;
- and no further. When the site answers by sending the request on to another site, at once or
  after a few steps of its own, the request stops there.

This is what keeps a web page from talking a bot into typing your password somewhere else. The bot
proposes the site when it asks, the card shows it before you type, and afterwards only you can
change it.

## How a bot uses one

- **In a request.** `web_fetch` takes a method, headers and a body, and the bot writes
  `{{secret:plausible}}` where the key goes:

  ```json
  {
    "url": "https://plausible.io/api/v2/query",
    "method": "POST",
    "headers": { "Authorization": "Bearer {{secret:plausible}}" },
    "body": "{\"site_id\": \"openkumi.ai\", \"metrics\": [\"visitors\"], \"date_range\": \"7d\"}"
  }
  ```

- **In a page.** `browser_type` takes `secret` instead of `text`, and the value is typed into the
  field, if the page showing is one of the secret's site.

A bot can run scripts of its own in a page (`browser_eval`), and a script could read a secret out
of a page and hand it over in another shape. So the two are kept apart: a bot runs no script on a
site one of its secrets is for, or was put into a page of in that browser window, and a secret is
not typed in a browser window where the bot has already run a script on that site. In that case a
subagent, which has a window of its own, does the typing.

What comes back to the bot is searched for the value, and the secret's name is put in its place:
a service that repeats the key it was sent, or a field that still holds a password, reads as
`[secret: plausible]`. A long value is known by how it begins, so a page that shows only the
first part of a token gives nothing away either.

A bot can also keep a secret itself, with `save_secret`: a key that a page showed it while it set
something up for you, or a password for an account it signs up for. For a password it can have
OpenKumi make one up, which it then types by name and never sees. A bot cannot replace or remove a
secret, nor read one back. When a key has stopped working, the bot can ask for it again; the card
then says that what you type takes the place of the one it has.

## Looking after them

**Settings → Bots →** the bot **→ Secrets** lists each secret: what it is, where it is sent, who
put it there (you or the bot) and when it was last used.

- **Add a secret** under a name that is free. Adding never writes over one that is there.
- **Change** what it is or where it may go, or give it a new value.
- **Remove** it. A secret the bot kept itself may be written down nowhere else.
- **Show** its value. Only the computer that runs OpenKumi is given a value: another computer or
  an iPhone can add, change and remove secrets, but not read one back.

Each bot has its own vault, as it has its own logins. Give two bots the same key by adding it to
both.

## Where a secret is kept

Values are encrypted (AES-256-GCM) in the bot's private folder, which its file tools cannot reach:
`bots/<id>/private/secrets.json`. The key they are encrypted with is yours alone, one for each
person with bots on the computer, and it is kept apart from your data:

| The computer that runs OpenKumi | Where the key is |
| --- | --- |
| A Mac | The login keychain, as **OpenKumi vault** |
| Windows | A file that Windows opens only for your account on that computer |
| Linux with a desktop keyring | The keyring (through `secret-tool`) |
| Linux without one, such as a server | A file only your account can read: `~/.config/openkumi/keys/` |

Where the keychain, Windows or the keyring cannot take the key at the moment the first secret is
saved (a Mac reached over ssh with nobody logged in, say), the key is a file only your account can
read instead: in `~/.config/openkumi/keys/`, on Windows in `%LOCALAPPDATA%\OpenKumi\keys`. The
bot's **Secrets** tab says where the key is.

So a copy of your data folder is not enough to read a secret: not a backup, not a folder that is
synced somewhere, not the folder sent to somebody.

It also means that the secrets do not travel with the folder. Moved to another computer, or
restored after the keychain was reset, they are still listed, each marked as unreadable. Enter
them again there; nothing else is lost.

## What the vault does not do

- **It does not stop a program that runs as you.** Whatever runs under your account on that
  computer can ask for the key the way OpenKumi does. The vault protects copies of your data, not
  a computer somebody else already controls.
- **It does not stop a bot being fooled on the right site.** A secret only goes to its site, but
  a bot that is talked into misusing it there still can: an API key for a service can do whatever
  that key allows. Make keys that can do no more than the work needs.
- **It finds a value as it was sent.** A site that hands a key back in another shape (cut in two,
  encoded) is not caught, and the bot would read it. A value shorter than six characters, such as
  a PIN, is not looked for at all: it would be found in text that has nothing to do with it.
- **It cannot reach what others keep.** A key that was written in a message has been read by the
  AI service, and Claude Code, Codex and Grok keep their own records of a conversation.

See also [What OpenKumi does not protect against](/security/limits/).
